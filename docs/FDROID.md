# F-Droid Deployment Guide for maripànaTokana

## Overview

This document describes how maripànaTokana is configured for F-Droid deployment, including the build process, flavors, and maintenance requirements. The app is currently listed on F-Droid as [`orinasa.njarasoa.maripanatokana`](https://f-droid.org/packages/orinasa.njarasoa.maripanatokana/).

A hosted instance of the Web (PWA) version, kept in feature parity with the Android app, is available at [maripana.njarasoa.org](https://maripana.njarasoa.org) — no install needed.

## Gradle/JDK Configuration for F-Droid CI

F-Droid's build server runs OpenJDK 21. Kotlin 2.x defaults to requesting JetBrains JDK 21 for the compiler daemon. If the build config isn't set up correctly, CI fails. This section documents every setting that matters and why.

### `app/build.gradle.kts`

**`kotlin { jvmToolchain(21) }` — CRITICAL, DO NOT REMOVE**

This overrides Kotlin 2.x's default JetBrains JDK vendor requirement with a vendor-agnostic JDK 21 spec. Without it, the build fails with:

> "Cannot find a Java installation matching: {languageVersion=21, vendor=JetBrains}"

**Plugins — DO NOT add `id("org.jetbrains.kotlin.android")`**

AGP 9.x + the compose plugin already register the `kotlin` extension. Adding `kotlin.android` explicitly causes:

> "Cannot add extension with name 'kotlin', as there is an extension already registered"

The correct plugins are exactly:
```kotlin
plugins {
    id("com.android.application")
    id("org.jetbrains.kotlin.plugin.compose")
    id("org.jetbrains.kotlin.plugin.serialization")
    id("com.google.devtools.ksp")
    id("com.google.dagger.hilt.android")
}
```

### `settings.gradle.kts`

**DO NOT add `org.gradle.toolchains.foojay-resolver-convention` or any toolchain download plugin.**

F-Droid's security scanner (`fdroid-suss`) flags foojay as a supply-chain risk:

> "Found usual suspect 'org.gradle.toolchains.foojay-resolver' at settings.gradle.kts"

The file should have no `plugins {}` block — just `pluginManagement`, `dependencyResolutionManagement`, and project includes.

### `gradle.properties`

**`org.gradle.java.installations.auto-provisioning=disabled` — MUST stay disabled**

F-Droid doesn't allow downloading JDKs during builds. Combined with `jvmToolchain(21)` (vendor-agnostic), the build uses whatever JDK 21 is already on the server.

**`org.gradle.parallel=true` and `org.gradle.caching=true`** make local and CI builds faster. They do not change the APK: the F-Droid check in the release workflow compares the APKs byte for byte.

**`dependenciesInfo { includeInApk = false; includeInBundle = false }` — MUST stay in `app/build.gradle.kts`**

AGP 8+ embeds a "Dependency metadata" block in the APK's signing block by default. F-Droid's `fdroid-suss` scanner rejects any APK containing this block:

> "Found extra signing block 'Dependency metadata'"

Without this block, `check apk` fails even when the build and reproducibility checks pass. `gradle.properties` also has `android.dependenciesInfo.includeInApk=false` and `android.dependenciesInfo.includeInBundle=false`. Keep both, but the `dependenciesInfo` block in `app/build.gradle.kts` is the setting to check first.

### `gradle/gradle-daemon-jvm.properties`

**Must only contain `toolchainVersion=21` — NO `toolchainVendor` or `toolchainUrl` lines.**

This controls the Gradle daemon's JVM. If `toolchainVendor=JETBRAINS` is present, Gradle itself won't start on F-Droid's server. The file is auto-generated by `./gradlew updateDaemonJvm` — if it ever gets vendor lines, remove them.

### F-Droid Metadata (`metadata/orinasa.njarasoa.maripanatokana.yml`)

**No `prebuild` steps should be needed.** If the Gradle config above is correct, the build entry is simple:

```yaml
Builds:
  - versionName: X.Y.Z
    versionCode: N
    commit: <full commit hash>
    subdir: app
    gradle:
      - fdroid
```

No inline `Description` field — use fastlane structure instead (reviewer requirement).

**`Binaries:` field — trailing space is mandatory.** The canonical format that `fdroid rewritemeta` enforces is:

```
Binaries: 
  https://github.com/mpilasy/maripanaTokana/releases/download/v%v/maripanaTokana-v%v.apk
```

The line must be `Binaries: ` — colon, **space**, then newline — with the URL indented two spaces on the next line. A missing trailing space causes the `fdroid rewritemeta` GitLab CI job to fail even though all other jobs pass. The GitHub CI validates this before pushing to GitLab (`grep -P '^Binaries: $'`). If that check fires, fix the file and re-run.

### `app/proguard-rules.pro`

**R8 keep rules — CRITICAL for release builds**

Release builds use `isMinifyEnabled = true` and `isShrinkResources = true`. `proguard-rules.pro` has three groups of keep rules, and all must stay:

- **Room and WorkManager.** WorkManager uses Room internally (`WorkDatabase_Impl`), and Room-generated `_Impl` classes are instantiated via reflection. R8 strips their no-arg constructors, causing a `NoSuchMethodException` crash at startup.
- **Location.** `LocationListener` implementations and the `data.location` package, for `NativeLocationProvider` (F-Droid flavor).
- **Kotlin Serialization.** All `@Serializable` classes in `data.remote` and their `$$serializer` classes. Without them, R8 removes fields that only the generated serializers use, and the API responses do not parse.

The Room and WorkManager rules:

```proguard
# Room: keep generated _Impl classes (instantiated via reflection)
-keep class * extends androidx.room.RoomDatabase { <init>(); }
-keep class * implements androidx.room.DatabaseConfiguration { *; }
-keep class **_Impl { <init>(); }

# WorkManager: uses Room internally for WorkDatabase
-keep class androidx.work.impl.** { *; }
```

Without these rules, the app crashes immediately on startup in any minified build.

### Quick Diagnostic Checklist

If the **GitHub Actions build** or a local build fails, check in order:

1. Is `kotlin { jvmToolchain(21) }` present in `app/build.gradle.kts`? (missing = JetBrains JDK error)
2. Is `kotlin.android` applied in `app/build.gradle.kts`? (present = extension conflict). The root `build.gradle.kts` declares it with `apply false`, which is correct.
3. Does `gradle-daemon-jvm.properties` have `toolchainVendor`? (present = Gradle daemon won't start)
4. Are the R8 keep rules in `proguard-rules.pro`? (missing = crash at startup, or API responses that do not parse)
5. Does `metadata/*.yml` have `Binaries: ` with trailing space? The workflow checks this with `grep -P '^Binaries: $'`.

These problems show only on F-Droid's GitLab pipeline:

1. Is foojay in `settings.gradle.kts`? (present = fdroid-suss blocks it)
2. Is `auto-provisioning` set to `enabled`? (will try to download JDKs and fail)
3. Is `dependenciesInfo` missing from `app/build.gradle.kts`? (missing = `check apk` fails)

If the **GitLab MR pipeline** fails, check which job failed. The jobs are: check apk, check source code, schema validation, tools check scripts, fdroid rewritemeta, fdroid lint, git redirect, checkupdates and fdroid build.

- **`fdroid build`** — actual Gradle build failure. Look at the job log for Kotlin/Gradle errors. A 404 on the `Binaries` URL means that the GitHub release APK does not exist yet. Wait for the release workflow, then retry the job.
- **`checkupdates`** — a tag exists that is newer than `CurrentVersion` in the yml. Add the build entry for the newest tag, or let the bot add it and rebase the MR.
- **`check apk`** — APK has disallowed signing block or Google Play dependency. Check the `dependenciesInfo` block in `app/build.gradle.kts`.
- **`check source code`** — `fdroid-suss` found a blocked library or plugin in the source, for example foojay.
- **`fdroid lint`** — metadata YAML syntax error. Validate with a YAML linter.
- **`fdroid rewritemeta`** — metadata is not in canonical format. Download the job artifact (`tmp/orinasa.njarasoa.maripanatokana.yml`) to see the diff of what `fdroid rewritemeta` would change. The most common cause is the `Binaries:` trailing space (see above).
- **`schema validation`** — missing required field or wrong field type in the YAML.

**Debugging `fdroid rewritemeta` failures:** The job saves the reformatted file as an artifact in `tmp/`. Download it and diff against the committed file to see exactly what byte-level difference `fdroid rewritemeta` detected. The GitLab API path is:
```
GET https://gitlab.com/api/v4/projects/mpilasy%2Ffdroiddata/pipelines/<id>/jobs
# find the fdroid rewritemeta job id, then:
GET https://gitlab.com/api/v4/projects/mpilasy%2Ffdroiddata/jobs/<job_id>/artifacts
# follow the redirect, unzip, read tmp/orinasa.njarasoa.maripanatokana.yml
```

**Why the GitHub CI runs `fdroid rewritemeta` locally but doesn't trust its output:** The "UPDATE METADATA AND PUSH" step in `fdroid-build.yml` runs `fdroid rewritemeta` before pushing so a hard failure (real schema/lint error) still fails the GitHub job. But its *reformatted* output is discarded — the step snapshots the file before running it and restores the snapshot if `fdroid rewritemeta` changed anything, keeping `scripts/update_metadata.py`'s canonical output instead. This exists because `fdroid rewritemeta`, run locally, was observed (2026-07-02, v1.2.1 release) to non-deterministically rewrite semantically-identical YAML into a form GitLab's own `fdroid rewritemeta` job then rejected: it collapsed the `Binaries: ` trailing-space two-line form into one line, and re-wrapped the `mg-MG` AntiFeatures double-quoted block scalar from plain continuation into `\`-escaped continuation. No `fdroidserver`/`ruamel.yaml` version had changed between the prior successful run and this one, so the local tool's output isn't safe to push as-is — only `update_metadata.py`'s targeted edits are.

### Approaches That Were Tried and Failed

| Approach | Error |
|---|---|
| foojay-resolver plugin | `fdroid-suss` blocks it as supply-chain risk |
| `auto-provisioning=enabled` | F-Droid blocks JDK downloads |
| Adding `kotlin.android` plugin | "Cannot add extension with name 'kotlin'" conflict |
| `prebuild` sed hacks in metadata | Fragile; the sed for kotlin.android caused the same conflict |
| `Binaries: URL` inline (no trailing space/newline) | `fdroid rewritemeta` reformats it, causing `git diff --exit-code` to fail |
| `Binaries:\n  URL` without trailing space on first line | Same — rewritemeta adds the trailing space and fails the diff |
| No `jvmToolchain(21)` at all | Kotlin defaults to JetBrains vendor |
| No R8 keep rules for Room/WorkManager | `NoSuchMethodException: WorkDatabase_Impl.<init>` crash at startup |

## Build Flavors

The app has two build flavors configured in `app/build.gradle.kts`:

### Standard Flavor
- Uses Google Play Services for location (`libs.play.services.location` and `libs.kotlinx.coroutines.play.services`)
- Includes Accompanist Permissions library for permissions UI
- Uses `PlayServicesLocationProvider` for location
- Default geocoder: the system geocoder (`DefaultSettings.kt`)
- Published only on GitHub releases, as `maripanaTokana-standard-vX.apk` (for Obtainium). The app is not on Google Play.
- Built with: `./gradlew assembleStandardRelease`

### F-Droid Flavor
- Uses only native Android `LocationManager` (no Google Play Services)
- Uses simplified permissions handling without Accompanist
- Uses `NativeLocationProvider` for location services
- Default geocoder: Nominatim (`DefaultSettings.kt`)
- Fully compatible with F-Droid's requirements
- Built with: `./gradlew assembleFdroidRelease`

## Location Provider Architecture

### LocationProvider Interface
Located at: `app/src/main/java/orinasa/njarasoa/maripanatokana/data/location/LocationProvider.kt`

Provides two methods:
- `getLastLocation()`: Returns cached location from device
- `getFreshLocation()`: Requests a fresh location update. Each implementation sets its own timeout (see below)

### Implementations

#### PlayServicesLocationProvider (Standard)
Location: `app/src/standard/java/.../PlayServicesLocationProvider.kt`
- Uses FusedLocationProviderClient from Google Play Services
- Higher accuracy, better battery efficiency
- Uses PRIORITY_BALANCED_POWER_ACCURACY
- 10-second timeout for fresh location requests

#### NativeLocationProvider (F-Droid)
Location: `app/src/fdroid/java/.../NativeLocationProvider.kt`
- Uses Android's built-in LocationManager
- Supports GPS_PROVIDER, NETWORK_PROVIDER and PASSIVE_PROVIDER
- `getLastLocation()` takes the more recent of the GPS and network fixes, and ignores fixes older than 24 hours
- `getFreshLocation()` takes the first fix from any of the three providers
- 30-second timeout for fresh location requests. On timeout, it uses a cached fix if one is less than 24 hours old

## Dependency Injection

Flavor-specific DI modules provide the appropriate LocationProvider:

### Standard Flavor Module
Location: `app/src/standard/java/.../di/LocationModule.kt`
- Provides `FusedLocationProviderClient`
- Provides `PlayServicesLocationProvider` as `LocationProvider`
- `LocationBindingModule` in the same file binds `StandardPermissionHandler` as `PermissionHandler`

### F-Droid Flavor Module
Location: `app/src/fdroid/java/.../di/LocationModule.kt`
- Provides `NativeLocationProvider` as `LocationProvider`
- `LocationBindingModule` in the same file binds `FDroidPermissionHandler` as `PermissionHandler`
- No Play Services dependencies required

## UI Adaptations

### Permission handlers
`WeatherScreen` is shared code. The flavors differ in their implementation of the `PermissionHandler` interface (`app/src/main/.../ui/permission/PermissionHandler.kt`):

**Standard Flavor** (`app/src/standard/.../ui/permission/StandardPermissionHandler.kt`)
- Uses the Accompanist Permissions library
- Uses `rememberMultiplePermissionsState` for the fine and coarse location permissions

**F-Droid Flavor** (`app/src/fdroid/.../ui/permission/FDroidPermissionHandler.kt`)
- Uses the AndroidX activity result API and `ContextCompat` directly
- Does not use Accompanist

The two flavors also use different location providers (see above), different `WidgetWeatherFetcher` classes and different `DefaultSettings.kt` files.

### WidgetWeatherFetcher
Flavor-specific widget location fetcher implementations:

**Standard Flavor** (`app/src/standard/.../widget/WidgetWeatherFetcher.kt`)
- Uses FusedLocationProviderClient directly

**F-Droid Flavor** (`app/src/fdroid/.../widget/WidgetWeatherFetcher.kt`)
- Uses native LocationManager
- Same functionality, F-Droid compatible

## Build Configuration

### Reproducible Builds

The F-Droid flavor is configured for reproducible builds:

1. **BUILD_TIME buildConfigField**
   - Standard flavor: the local build time (`yyyy-MM-dd HH:mm`), shown in the footer
   - F-Droid flavor: "reproducible" string (for byte-identical builds). The F-Droid flavor also sets `DISTRIBUTION="fdroid"`

2. **GIT_HASH buildConfigField**
   - The short hash of `HEAD`. It is the same for every build of the same commit, so it does not break reproducibility

3. **PNG Crunching**
   - Disabled in release builds for reproducibility (`isCrunchPngs = false` in `app/build.gradle.kts`)

4. **No dependency metadata**
   - The `dependenciesInfo` block (see above) keeps the signing block identical

5. **Consistent Dependencies**
   - Version-locked in `libs.versions.toml`
   - F-Droid flavor excludes Play Services

### Signing

F-Droid checks that its own build matches the APK at the `Binaries` URL, except for the signature. Then it publishes our signed APK. So all release APKs must use the same key:

- The metadata has `AllowedAPKSigningKeys`, the SHA-256 fingerprint of our signing certificate. `scripts/update_metadata.py` writes it.
- The release workflow gets the key from the GitHub secrets `KEYSTORE_BASE64`, `KEYSTORE_PASSWORD`, `KEY_ALIAS` and `KEY_PASSWORD`.
- A local release build is signed only when `keystore.properties` exists or `KEYSTORE_FILE` is set. Otherwise the APK is `app-fdroid-release-unsigned.apk`.

## Maintenance and Updates

### For Future Versions

Releases are usually made by hand:

1. Audit the dependencies (`gradle/libs.versions.toml`, and `npm outdated` and `npm audit` in `web/`), and apply small updates.
2. Bump the version in `app/build.gradle.kts` (`versionCode` and `versionName`), `web/package.json`, `web/package-lock.json` (2 entries) and `web/src/lib/components/Footer.svelte`.
3. Write `fastlane/metadata/android/{locale}/changelogs/{versionCode}.txt` in all 8 locales (ar, en-US, es, fr, hi, mg, ne, zh-CN). Keep each file under 500 characters. F-Droid builds only the newest tag, so its page shows only the newest file. The file must cover every version that is not yet on the F-Droid page at release time: all versions newer than `suggestedVersionCode` from `https://f-droid.org/api/v1/packages/orinasa.njarasoa.maripanatokana`. Put the newest change first. When the lines do not fit in 500 characters, shorten them or combine them into a summary; do not drop a version.
4. Add an entry at the top of `CHANGELOG.md` (move the Unreleased items into it). Each release must have notes: the GitHub release shows this entry.
5. Run `python3 scripts/check_version_sync.py`. It fails when the version strings differ, or when the current version has no `CHANGELOG.md` entry or no changelog file in one of the 8 locales.
6. Commit as `Bump to vX.Y.Z`, push `main`, then create and push the tag `vX.Y.Z`.

Version names (after 1.6.0): `MAJOR.MINOR.YYYYMMDDHHMMSS`, with the release time in UTC as the third number, for example `1.6.20261027143005`. Each release gets a new, higher version, also two releases on the same day. UTC has no clock changes, so the order is always correct. The version stays valid semver. `versionCode` still adds 1 for each release.

Do not edit `metadata/orinasa.njarasoa.maripanatokana.yml` by hand. The release workflow updates it.

`scripts/release_fdroid.sh` can do steps 2, 5 and 6:
```bash
./scripts/release_fdroid.sh [VERSION_NAME] [VERSION_CODE]
# Example: ./scripts/release_fdroid.sh 1.6.20261027143005 114
# Without arguments, the version is MAJOR.MINOR.YYYYMMDDHHMMSS (now, in UTC). The version code adds 1.
```

Write the changelogs and the `CHANGELOG.md` entry first. The script stops if a changelog file or the `CHANGELOG.md` entry is missing.

The script performs these steps:
1. Updates the version in `app/build.gradle.kts`, `web/package.json` and `web/src/lib/components/Footer.svelte`.
2. Runs `npm install --package-lock-only` in `web/` to update the lock file.
3. Validates the version sync and the release notes with `python3 scripts/check_version_sync.py`.
4. Checks that the changelog exists in all 8 locales.
5. Commits all pending changes as `Bump to vX.Y.Z`.
6. Creates the tag `vX.Y.Z` on the bump commit.
7. Updates the F-Droid metadata with `python3 scripts/update_metadata.py` and checks the `Binaries: ` line.
8. Commits the metadata with `[skip ci]`.
9. Pushes `main` and the tag.

The tag push starts `.github/workflows/fdroid-build.yml`. The workflow takes about 10 minutes. It has four jobs:
1. `build`: checks the release notes first and stops when `CHANGELOG.md` has no entry for the tag (`scripts/release_notes.py`). Then builds the F-Droid and standard flavors (`assembleFdroidRelease assembleStandardRelease`). The Gradle files come from the cache that `ci.yml` saves on `main` (`setup-java` with `cache: 'gradle'`).
2. `fdroid`: at the same time as `build`, does F-Droid's build of the tag (`scripts/fdroid_check.sh --build-only`).
3. `scan`: after `build`, scans both APKs on VirusTotal, at the same time as `fdroid`.
4. `release`: after the other three, compares our F-Droid APK with F-Droid's build (`scripts/fdroid_compare.py`). Then runs `scripts/update_metadata.py` again, validates the `Binaries: ` line, and pushes an `Update F-Droid metadata for vX.Y.Z [skip ci]` commit to `main` if the file changed. Pull this commit before the next change. Last, creates a GitHub release with the `CHANGELOG.md` entry as its notes and two APKs: `maripanaTokana-vX.Y.Z.apk` (F-Droid flavor) and `maripanaTokana-standard-vX.Y.Z.apk` (standard flavor).

A manual run (`workflow_dispatch`) does the same jobs on `main`, but does not update the metadata or make a release.

Each push to `main` also starts `ci.yml` (i18n parity, Android unit tests and lint, web check, tests and build) and `version-sync-check.yml`.

F-Droid verifies its own build against the F-Droid APK through the `Binaries:` field. It does not use the standard APK.

Do not push to the old fork branch (`add-maripanatokana`). It is dead. F-Droid's bot finds new tags (`UpdateCheckMode: Tags`, `AutoUpdateMode: Version`), and opens and merges its own `bot: Update maripànaTokana to {versionCode}` MR against `fdroid/fdroiddata`. The bot runs once a day, at about 05:00 UTC. It adds only the newest tag it finds, so F-Droid skips some versions if you push more than one tag between runs. It also removes older build entries, so a version that was added but not yet built can be dropped (1.5.24 was replaced by 1.5.28). Check the status with:
```
curl -s "https://gitlab.com/api/v4/projects/fdroid%2Ffdroiddata/merge_requests?search=Tokana&in=title&per_page=5&order_by=updated_at"
```

### How Long a Release Takes

After the bot merges a version, F-Droid builds it in its next build cycle, then signs and publishes the cycle. A cycle takes some days, and a new one starts only after the last one ends. Example, 1.5.22 (October 2026):

| Step | Time after the tag |
|---|---|
| GitHub release | 8 minutes |
| Bot MR merged | 7 hours |
| Build cycle starts | 22 hours |
| Build cycle ends (51 hours) | 73 hours |
| Live on F-Droid | 87 hours |

A version that misses a cycle waits for the next one, so it can take a week. Obtainium users get each release from GitHub at once. F-Droid's build status is at `https://f-droid.org/repo/status/running.json`.

### Screenshots

The store has exactly 4 screenshots per language (`1.png` to `4.png`, 32 in total). Save them to `fastlane/metadata/android/{locale}/images/phoneScreenshots/`. A push of screenshots does not start a release. They reach F-Droid with the next release tag. For the capture method, see [SCREENSHOTS_README.md](./SCREENSHOTS_README.md).

### Localization Updates

If i18n translations are updated:
1. Update JSON files in `shared/i18n/locales/`
2. Run: `node shared/i18n/generate-android-strings.js`
3. Run: `node scripts/check_i18n_parity.js`
4. Commit the JSON files and the generated `app/src/main/res/values*/strings.xml` files. Gradle does not run the generator, and F-Droid builds from the committed `strings.xml` files.
